Few-shot examples and task decomposition

Two tools for when instructions alone are not enough: show the model what you want, and give it less to do at once. Both come with a trap.

1. Showing instead of telling

A prompt with instructions and no examples is called zero-shot. Add a few worked examples, input and correct output, and it becomes few-shot. The model's parameters do not change at all: nothing is trained. The examples are just more text in the context, and the model continues the pattern it sees. This is called in-context learning, and it is one of the more surprising abilities of large language models.

Examples carry information that is hard to put in words:

  • the exact output format, down to capitalisation and field order;
  • how fine-grained to be;
  • how to resolve cases where your rules are silent or collide.

There are two common ways to supply them. You can write them inside the system prompt, in tags. Or you can stage them as earlier turns of the conversation: a user message with the input, then an assistant message with the ideal output, repeated. The second form shows the model its own "previous answers" in precisely the format you want next.

2. The linguist's example: the minimal pair

Linguists have a standard instrument for isolating one distinction: the minimal pair. Two items identical except for a single feature, where that one difference changes the outcome. Pat and bat differ in one sound and mean different things, which proves that /p/ and /b/ are distinct sounds of English. The same method works for grammar:

PairWhat differsWhat it shows
She can fish.
She cans fish.		one letterfish is VERB in the first, NOUN in the second; can flips from AUX to VERB
ذهبَ الولد
ذهبُ الولد		one vowel mark"the boy went" (VERB) against "the boy's gold" (NOUN)

A minimal pair is the most efficient few-shot example there is. Because everything else is held constant, the model can only attribute the change in output to the feature you care about.

3. Choosing examples under a budget

Every example is input tokens, paid on every single request (Lesson 3). So the question is never "how many examples can I add" but "which few earn their place". Good sets share three properties:

  • They cover the hard cases. The model already tags The cat sleeps correctly. An example of it teaches nothing.
  • They show both sides. One example of that as SCONJ, with no contrasting DET, teaches "that is SCONJ".
  • They look like real input. Same length, same style, same language mix as what will actually arrive.

4. The traps

Examples are the strongest signal in a prompt, stronger than instructions. The model copies everything about them, including what you did not intend:

  • Label imbalance. If five of six examples contain a NOUN, expect too many NOUNs.
  • Surface copying. If every example is a five-word sentence, long inputs suffer. If every example is English, Arabic suffers.
  • Order effects. The last example weighs more than the first. Shuffle and re-test.
  • Mistakes are contagious. One wrong tag in an example will be reproduced faithfully. Check examples harder than anything else in the prompt.

When instructions and examples disagree, the examples usually win. So keep them consistent, and when output looks odd, read your examples before you rewrite your rules.

5. Decomposition: give it less to do at once

Some tasks are several tasks in a coat. Arabic tagging is the clearest case. In Universal Dependencies the unit that gets a tag is the syntactic word, and one written Arabic word often contains several: وكتابها, "and her book", is a conjunction, a noun and a pronoun written without spaces. A prompt that asks for "one tag per word" forces a wrong answer before the model has begun.

Split a task when its parts need different instructions, when an early decision determines everything after it, or when you want to test and fix the parts separately. Do not split when the parts need each other's context to be done well, because each call sees only what you pass along. Lesson 8 is entirely about building and checking such chains.

6. Room to think

A model generates left to right and cannot revise. If the first thing you make it produce is the final answer, it must commit before any reasoning has been written down. Letting it write intermediate steps first often improves hard, multi-step judgements. In structured output this is just a field ordering choice from Lesson 4: put a reasoning field before the answer field.

It is not free. Reasoning is output tokens, the expensive kind, and it adds latency. Use it where decisions are hard, such as an ambiguous ذهب, and skip it for the thousands of easy words. Many current models also offer a built-in "thinking" or "reasoning" mode that does this internally; check your model's documentation for how it is switched on and billed.
