Caching, model routing, cost control

A prototype's bill is a curiosity. A service's bill is a design constraint. There are three honest ways to spend less: do not repeat work, do not use more model than a task needs, and do not let any request run without a limit. Each has a way of going wrong that costs you quality instead.

By the end you can

  • Choose among exact, normalised, prefix and semantic caching, and say when each returns a wrong answer.
  • Design a cascade that sends easy work to a cheap model without lowering quality.
  • Enforce budgets per request, per user and per day.
Answer to last lesson's question. The cheapest correct response to a question you have already answered is the stored answer: no model call at all. It becomes wrong when the question only looks the same, or when the right answer has changed since: the corpus was updated, the prompt was improved, the model was replaced. Caching is easy. Knowing when a cached answer is still valid is the whole difficulty.

1. Know where the money goes

Before optimising, measure. Your traces (Lesson 25) hold tokens per span, so you can total cost by span kind, by step number and by request. Three patterns show up in almost every agent:

  • Input dominates. Because history is re-sent at each step (Lesson 21), most tokens are input tokens, most of those are old tool results, and most of those are identical from one step to the next.
  • Cost is long-tailed. A few runs cost ten times the typical one. Report the p95 of cost, as you do for latency (Lesson 26).
  • A few steps matter. Often one call, the final report or a heavy tool result, accounts for a large share.

Each pattern points to a lever. Repeated identical input calls for caching. The long tail calls for limits. The heavy step calls for a closer look at that one prompt or tool.

The first three are safe and should be your defaults. You built the second in Lesson 12 for the eval harness; the same code serves production. Prefix caching suits agents especially well, because each step's request begins with everything the previous step sent.

Whatever the kind, the hard part is invalidation: knowing when an entry must no longer be used. Put every input that affects the answer into the key (model ID, prompt version, corpus or index version) so that changing any of them misses automatically. Add an expiry time for anything that depends on the outside world.

3. When are two questions the same question?

This is a question about meaning, and you have the tools from this course to see why it is treacherous. Lexical similarity and semantic similarity diverge (Lesson 15). Embeddings place safe and not safe side by side (Lesson 2). A semantic cache stakes correctness on a similarity score.

Try it · 1

Tune a cache

Twelve requests arrive in order. Similarity here is plain word overlap, a stand-in for embedding similarity that fails in the same ways. Each request has a true intent, so wrong hits can be counted.

Experiments. Start with exact, then normalised: every hit is correct. Now similarity at 0.80: which request is answered wrongly, and what single word made the difference? Lower the threshold to 0.65 to catch the paraphrases. What else gets caught? There is no threshold that catches every rewording and no wrong answer.

So a semantic cache is a retrieval system with a correctness requirement, and it gets treated like one: an eval set of question pairs labelled same or different, a threshold chosen on that set, wrong-hit rate monitored in production (Lesson 26). Many teams find that normalisation plus exact matching captures most of the savings with none of the risk, and stop there.

4. Use no more model than the task needs

Model prices span a wide range, and many requests are easy. Routing sends each request to the cheapest model that can handle it. Three ways to decide:

  • Rules. By task type, language or length. Tagging English sentences goes to the small model; Arabic segmentation to the large one.
  • A classifier. A small model, or a few lines of code, predicts difficulty.
  • A cascade. Try the cheap model first. Accept its answer if it passes a gate; otherwise escalate to the strong model. No prediction needed: the gate decides after the fact.

The cascade is the most useful, and it depends entirely on the gate. You have built gates since Lesson 8: schema checks, invariants, the citation verifier. A cascade is safe to the extent that its gate catches the cheap model's bad answers. An answer that is wrong and passes is served to the user.

Try it · 2

Price a cascade

Experiments. At a price ratio of 2, how often must the cheap model pass before the cascade saves anything? Why? Then set wrong passes to 15%: the savings are unchanged and the product is worse. The third slider is the quality of your gate, and it is the one number here you can only learn from an eval.

5. Budgets are enforced, not hoped for

The whole servicespend per daya circuit breaker: switch to a cheaper mode or stop accepting work, and alert a person

The last row exists for the day something loops, or someone scripts ten thousand requests. Without it, the first you hear of the problem is the invoice. Decide in advance what the service does when money is tight: serve cached answers only, use the cheap model only, cover fewer genres. A planned, announced reduction is called graceful degradation, and it beats both an outage and an unlimited bill.

6. The order to pull levers in

  1. Stop waste. Smaller tool results (Lesson 20), compaction (Lesson 21), fewer examples (Lesson 6), shorter stable prompts (Lesson 7). These lower cost and usually raise quality.
  2. Add safe caches. Tool results, exact responses, provider prefix caching.
  3. Enforce budgets. They cost nothing and cap the worst case.
  4. Route. A cascade behind a gate you have measured.
  5. Only then, consider semantic caching or dropping to a weaker model everywhere, with the eval harness open.

The rule running through all five: every cost change is a system change, so it goes through the harness (Lesson 12) and is reported as cost and quality together (Lesson 24). For work with no person waiting, such as running an eval or annotating a corpus overnight, also check whether your provider offers discounted batch processing.

Checkpoint

Lab: halve the bill, keep the score

Time: 2.5 hours.

import hashlib, json, time

class Cache:
    def __init__(self, path, ttl_seconds=None):
        self.path, self.ttl = path, ttl_seconds
        try:
            self.data = json.load(open(path, encoding="utf-8"))
        except FileNotFoundError:
            self.data = {}
        self.hits = self.misses = 0

    def get_or_compute(self, key_parts, fn):
        key = hashlib.sha256(json.dumps(key_parts, sort_keys=True, ensure_ascii=False).encode()).hexdigest()
        entry = self.data.get(key)
        if entry and (self.ttl is None or time.time() - entry["at"] < self.ttl):
            self.hits += 1
            return entry["value"]
        self.misses += 1
        value = fn()
        self.data[key] = {"value": value, "at": time.time()}
        json.dump(self.data, open(self.path, "w", encoding="utf-8"), ensure_ascii=False)
        return value

def cascade(question, cheap, strong, gate):
    """gate(answer) returns a list of problems; empty means accept."""
    answer = run_agent(question, model=cheap)
    problems = gate(answer)
    if not problems:
        return answer, "cheap"

class DailyBudget:
    def __init__(self, limit_usd):
        self.limit, self.spent, self.day = limit_usd, 0.0, time.strftime("%Y-%m-%d")
    def charge(self, usd):
        today = time.strftime("%Y-%m-%d")
        if today != self.day:
            self.day, self.spent = today, 0.0
        self.spent += usd
    def allow(self):
        return self.spent < self.limit
