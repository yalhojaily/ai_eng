Why evals come first; building a test set

In Phase 2 you improved prompts by reading outputs and counting mistakes by hand. That works for twenty sentences and one afternoon. This phase replaces your eyes with a program, so that every change is measured, every time.

Answer to last lesson's question. For a program to count errors for you, three things must exist: a fixed set of inputs, a known correct answer for each one, and a function that compares an output with its answer. Add a way to total the results and you have an evaluation, or eval.

1. What an eval is

datasetinputs + answers
→
runneryour system
→
scorercompare
→
reportnumbers + errors

The runner is your application, which you already have. The scorer and the report are a few dozen lines of code. The part that takes real work, and the part people skip, is the dataset. Without it every decision in an AI project (this prompt or that one, this model or a cheaper one, ship or wait) is made on impressions from the last few examples someone happened to look at.

This is why evaluation comes before more prompt work, more retrieval, more agents. It is the instrument that tells you whether any of those helped. Teams that build it early move faster, because they can change things without fear.

2. Linguists built the first eval datasets

Computational linguistics has measured systems against human-annotated corpora for decades. A corpus annotated with grammatical structure is called a treebank, and the annotations are the gold standard: the answers systems are scored against. The Universal Dependencies project you met in Phase 1 publishes treebanks for well over a hundred languages, all in one format, free to download.

How one is made matters for how far you trust it:

  1. Guidelines are written: what each tag means, how to treat hard cases.
  2. Annotators label the text, often two people independently.
  3. Disagreements are counted, then settled by discussion or a senior annotator (adjudication). Where annotators keep disagreeing, the guidelines are revised.
  4. The corpus is released with a version number, and errors found later are fixed in the next release.

Two lessons for you. First, gold is not truth. It is a convention applied by careful people, and it contains mistakes and judgement calls. Your system can be marked wrong for a defensible answer. Second, this is exactly the process you will follow for your own data, at a smaller scale.

3. Reading a treebank: CoNLL-U

UD treebanks are plain text files in CoNLL-U format. One line per word, ten tab-separated columns, a blank line between sentences, and comment lines starting with #. The columns you need now are the first four and the sixth:

ColNameHolds
1IDword number; a range such as 1-3 marks one written token that contains several syntactic words
2FORMthe word as written
3LEMMAdictionary form
4UPOSuniversal part-of-speech tag
6FEATSmorphological features, or _

Columns 7 and 8 give the syntactic head and relation (the "dependencies" in the name). An underscore means "nothing here".

4. Building your own test set

A public treebank is a fine starting point, but it tests the treebank's kind of text, usually news and web writing. Your application has its own inputs. A good test set for your system draws on three sources:

  • Real inputs. A sample of what actually arrives, chosen at random, not picked because it looked interesting.
  • Known failures. Every bug you have fixed becomes a permanent case, so it cannot return unnoticed.
  • Deliberate hard cases. The minimal pairs from Lesson 6, long sentences, mixed-language text, the injection sentence from Lesson 5.

Keep the mix representative. If 70% of your traffic is Arabic and your test set is 70% English, a high score tells you little. Record for each item where it came from and what kind it is, so that you can report scores by group: per language, per source, per difficulty. An overall average hides exactly the weak spots you most need to see.

Start small. Fifty carefully checked items beat five thousand unchecked ones, and you can begin measuring today. Grow the set as failures teach you what is missing.

5. How much can a small set tell you?

A test set is a sample, and a score on a sample is an estimate. Score 85% on 40 words and the true accuracy on all such text could plausibly be anywhere from the low 70s to the low 90s. The range in which the true value probably lies is a confidence interval, and it narrows only slowly: to halve it you need four times the data.

6. Two sets, not one

Every time you look at failures and adjust the prompt, you fit the prompt a little more closely to those particular items. After twenty rounds, the score on that set is flattering: the prompt has been shaped around it. So keep two sets:

  • A development set that you run constantly, read in detail, and tune against.
  • A test set that you run rarely, and never read item by item, to check that gains on the development set are real.

If the development score climbs while the test score stays flat, you have been memorising your examples, not improving the system. The same discipline protects against a quieter leak: few-shot examples copied from the test set. Any item that appears in a prompt must be removed from every set you score on.

Checkpoint

Lab: assemble your datasets

Time: 60 minutes. pip install conllu. Download two test files from the Universal Dependencies repositories on GitHub: en_ewt-ud-test.conllu from UD_English-EWT and ar_padt-ud-test.conllu from UD_Arabic-PADT.

import conllu, json, os, random
from collections import Counter

def load(path, n, seed=0):
    sentences = conllu.parse(open(path, encoding="utf-8").read())
    random.Random(seed).shuffle(sentences)          # fixed seed: same sample every run
    out = []
    for s in sentences[:n]:
        words = [t for t in s if isinstance(t["id"], int)]   # skip range lines like 1-3
        out.append({
            "text": s.metadata["text"],
            "tokens": [{
                "form": t["form"], "lemma": t["lemma"], "upos": t["upos"],
                "feats": "|".join(f"{k}={v}" for k, v in (t["feats"] or {}).items()) or "_",
            } for t in words],
        })
    return out

def save(items, path):
    with open(path, "w", encoding="utf-8") as f:
        for it in items:
            f.write(json.dumps(it, ensure_ascii=False) + "\n")

os.makedirs("data", exist_ok=True)
for lang, path in [("en", "en_ewt-ud-test.conllu"), ("ar", "ar_padt-ud-test.conllu")]:
    items = load(path, 100)
    save(items[:50], f"data/{lang}_dev.jsonl")
    save(items[50:], f"data/{lang}_test.jsonl")
    tags = Counter(t["upos"] for it in items for t in it["tokens"])
    print(lang, sum(tags.values()), "words", tags.most_common(5))

  2. Open the Arabic file in an editor and find three range lines. What kinds of word get split?
  3. Pick ten Arabic sentences from the treebank and compare its lemmas and tags with what you would have written. Note every place you disagree with the gold. Is the gold wrong, or is it a convention you did not know?
  4. Convert your own 30-sentence gold standard from Phase 2 to the same JSONL format, with a "source": "mine" field, and add "source": "ud" to the others.
  5. Check that none of your few-shot examples appears in any of these files.
