Running open models locally; quantization

Every model you have called so far ran on someone else's computer. A model whose weights you hold can run on yours. This lesson is about what that takes, what it buys, and the compression trick, quantization, that makes it possible on ordinary hardware.

Answer to last lesson's question. 1.5 billion parameters at 16 bits each is 3 billion bytes, about 3 GB, before any working memory. What you can give up is precision: store each number in 8 bits or 4 instead of 16. The model shrinks to a half or a quarter, runs faster, and loses a little accuracy. How little is something you measure.

1. Why run a model yourself?

ReasonWhat it means
PrivacyText never leaves your machine. For some data that is a requirement, not a preference.
StabilityThe model changes only when you change it. Lesson 26's silent provider update cannot happen.
Cost at volumeNo charge per token. For a narrow, high-volume task such as diacritising a library, the hardware pays for itself.
AvailabilityWorks offline, with no rate limits and no outages but your own.
Custom modelsYour fine-tuned model from Lesson 30 has to run somewhere.

The costs are equally real. The models you can run are much smaller than the strongest hosted ones and weaker at broad or difficult tasks. You become the operator: installation, updates, monitoring, capacity. And for low or bursty volume, paying per token is far cheaper than owning idle hardware. The usual result is a mix: small local models for narrow, private or high-volume steps, hosted models for the hard ones, joined by a router (Lesson 27).

2. Will it fit?

A model is its parameters, and they must sit in memory to be used. On a machine with a graphics card that means the card's own memory; on Apple Silicon, memory is shared between processor and graphics. The arithmetic is short:

memory ≈ parameters × bits per parameter ÷ 8      (bytes)
         + working space for the context           (grows with context length)
Try it · 1

Size a model

The estimate adds about 20% for working space, and a machine is counted as fitting when the model takes no more than 70% of its memory, leaving room for everything else. Experiments. What is the largest model a 16 GB machine can hold at 16 bits? At 4 bits? Find the size at which even 4-bit no longer fits in 24 GB.

3. Quantization

During training each parameter is a floating-point number with 16 or 32 bits of precision. Quantization replaces each with one of a small set of allowed values. With 4 bits there are only 16 possible values per number; with 8 bits, 256. The file stores which allowed value each parameter is nearest to, plus a little information for converting back.

Every parameter is now slightly wrong. The surprise, established by a great deal of experiment, is how tolerant large networks are of this: millions of small rounding errors mostly cancel. Down to about 8 bits the effect on quality is usually hard to measure. Around 4 bits it is small and often acceptable. Below that it tends to fall away quickly.

Try it · 2

Round some weights

Twelve example weights. Grey ticks are the allowed values, circles the original weights, and each line shows where a weight is moved to. Experiments. At 1 bit every weight becomes one of two values. How many bits before the average error falls below 0.01? Each extra bit halves the error and adds to the file size: that trade is the whole subject.

In practice you rarely quantize a model yourself. Open models are published in several ready-made precisions, with names indicating the bits. Your job is to pick one and measure it on your task. Published claims of "negligible loss" are averages over English benchmarks. Smaller and more heavily compressed models tend to lose more on languages and tasks that were thin in their training, so do not assume an Arabic letter-level task behaves like the average.

4. Running it: nothing in your code changes

Local model runners such as Ollama, llama.cpp and MLX load a model file and, usefully, expose it through a local web server that speaks the same chat format you learned in Lesson 3. Your client, your harness, your agent and your service work against a local model by changing one line:

client = OpenAI(base_url="http://localhost:11434/v1",   # a local server instead of a provider
                api_key="unused")                        # must be present; not checked locally
MODEL = "diacritizer"                                    # the name you gave your local model

That address is Ollama's default; other runners use other ports. Three details catch people:

  • Context length is a setting. Local runners often default to a small context window to save memory, and silently drop what does not fit. Set it explicitly to what your task needs.
  • The chat template matters. Each model family expects its own special tokens between turns (Lesson 3). Runners normally handle this from the model's metadata; a model that rambles or never stops usually has the wrong template.
  • Features vary. Structured output and tool calling (Lesson 4) depend on the runner and the model. Test them; do not assume.

5. Speed, and the language tax once more

Local speed is measured in tokens per second. It depends on the hardware, the model's size and its precision, and it is the number that decides whether a local model is usable for a person waiting or only for overnight batches.

Here the course comes full circle. In Lesson 1 you measured that Arabic takes more tokens per word than English. A machine generates tokens at a fixed rate whatever the language, so the same hardware produces Arabic text more slowly than English text. For diacritisation it is worse still: every letter gains a mark, so the output is far longer in tokens than the input.

6. Hosted or local: decide with numbers

You now have every instrument needed to make this choice properly, for one component at a time:

  1. Quality. Run the eval harness on each candidate: the hosted model, the local model at each precision. Same test set, same metrics (Lessons 12, 24).
  2. Speed. Tokens per second, time to first token (Lesson 3), and what that means in units your users feel.
  3. Cost. Per-token price times volume on one side; hardware, electricity and your time on the other (Lesson 27).
  4. Constraints. Privacy, offline use, stability. Some of these override the arithmetic.

Write the result as a small table and the decision usually makes itself. And because your client code is identical for both, it is not a one-way door: route to whichever is better for each kind of request, and revisit when the numbers change.

Checkpoint

Lab: your diacritiser on your own machine

Time: 2.5 hours. Install a local runner. The steps below use Ollama; MLX users can serve the fused model from Lesson 30 with mlx_lm.server instead, which offers the same kind of local endpoint.

# 1. A general small model, to confirm the plumbing
ollama pull <a small multilingual model>
ollama run  <that model> "أضف التشكيل: ذهب الولد إلى المدرسة"

# 2. Your own model. Convert the fused model from Lesson 30 to a GGUF file
#    (llama.cpp provides a conversion script and a quantize tool; see its README),
#    then describe it in a file named Modelfile:
#
#        FROM ./diacritizer-q4.gguf
#        PARAMETER temperature 0
#        PARAMETER num_ctx 2048
#
ollama create diacritizer -f Modelfile
import time
from openai import OpenAI

local = OpenAI(base_url="http://localhost:11434/v1", api_key="unused")

def diacritize(text, model="diacritizer"):
    start, first, pieces, n = time.time(), None, [], 0
    stream = local.chat.completions.create(
        model=model, temperature=0, stream=True,
        messages=[{"role": "user", "content":
                   "أضف التشكيل الكامل إلى النص التالي دون تغيير أي حرف:\n" + text}])
    for chunk in stream:
        piece = chunk.choices[0].delta.content if chunk.choices else None
        if piece:
            first = first or time.time() - start
            pieces.append(piece); n += 1
    elapsed = time.time() - start
    return "".join(pieces), {"first_token_s": first, "chunks_per_s": n / elapsed, "seconds": elapsed}
  1. Get step 1 working, and call the model from Python through the local endpoint. Then point your Lesson 12 harness at it by changing only the base URL and model name.
  2. Build your own model at two precisions, for example 8-bit and 4-bit. Note each file's size and compare with Try it 1's estimate.
  3. Run the 200 test sentences from Lesson 29 through each. One table: precision, file size, memory used, speed, DER and WER with and without case endings. Add the hosted baselines from Lesson 29 as rows.
  4. Where does the 4-bit model lose against 8-bit: case endings, word forms, or altering letters? Is the loss the same on your out-of-domain sample?
  5. Measure speed on vowelled output, and work out pages per hour on your machine. Would you use it interactively, or for batches?
  6. Set the context length too small on purpose and send a long paragraph. What comes back, and is there any warning?
  7. Write the hosted-or-local decision for this one component as a four-row table, following section 6.
