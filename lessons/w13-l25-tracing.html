Tracing and logging

So far your agent has run when you ran it, while you watched. In production it runs for other people, at other times, and you find out about problems afterwards. This phase is about operating the system: seeing what it did, noticing when it gets worse, paying less for it, and exposing it safely.

Answer to last lesson's question. To explain yesterday's strange answer you need, from that moment: the user's exact input; every request sent to the model and every response; every tool call with its arguments and result; which versions of the prompt, the model and the corpus index were in use; how long each step took and what it cost; and any error. You also need a way to find that one run among thousands. Record less and you are guessing.

1. Why AI systems need more recording than ordinary software

A conventional bug can usually be reproduced: give the same input, get the same wrong output, step through the code. A model-driven system often cannot be replayed. The model samples (Lesson 3), an agent takes a different path each run (Lesson 24), the provider may have updated the model, and the data may have changed. If you did not capture what happened, it is gone.

There is a second reason. In ordinary software the logic is in the code, which you can read. In an agent, much of the logic is in the model's choices, and those exist only in the record of a run. The trace is the source code of what actually happened.

2. Traces and spans

Three kinds of recording, each answering a different question:

  • Logs: timestamped messages. What events occurred?
  • Metrics: numbers aggregated over time. How is the system doing overall? (Lesson 26.)
  • Traces: the structured story of one request. What happened in this run, in what order, and where did the time go?

A trace is a tree of spans. A span is one unit of work: it has a name, a start time, an end time, a parent, and attributes. The whole request is the root span; each model call and each tool call is a child. Every span carries the same trace ID, which is how you pull one run out of a million. This vocabulary comes from the tracing of distributed systems and is standardised by the OpenTelemetry project, so the tools and habits you learn transfer.

Span kindAttributes worth recording
Request (root)trace ID, user or session ID, input, final output, outcome, total tokens and cost, versions of prompt, model, index
Model callmodel ID, parameters, messages sent (or a reference to them), response, input and output tokens, finish reason
Tool calltool name, arguments, size of result, the result or a reference to it, error if any
Retrievalquery, IDs and scores of what was returned
Gate / verifierpass or fail, the list of problems, whether a retry followed

The standard picture of a trace is a waterfall: one bar per span, positioned by start time and sized by duration. It answers at a glance the first two questions about any run: what took the time, and what happened just before things went wrong.

4. From traces to understanding: open coding

One trace explains one failure. To learn what is wrong with the system you need to read many, and reading many without a method produces only a vague unease. The method comes from qualitative research in the social sciences, where it is called open coding:

  1. Read a failure. Write a short free-text note on what went wrong, in your own words, without a fixed list of categories.
  2. Do that for fifty or a hundred.
  3. Group similar notes. Name the groups. These are your failure categories, and they came from the data.
  4. Count. The biggest group is your next piece of work.

This is Lesson 10's error analysis grown up. For a language system the categories are often linguistic, and knowing the levels of linguistic description gives you a head start on naming them:

5. Traces contain what people typed

The same completeness that makes a trace useful makes it sensitive. Users paste names, addresses, messages and documents into prompts, and tools fetch more. A trace store is a database of personal data unless you make it otherwise.

  • Redact before storing. Remove or mask obvious identifiers at the point of logging.
  • Limit retention. Keep full content for days or weeks, aggregates for longer.
  • Limit access. Fewer people should read raw traces than read dashboards.
  • Never log secrets. API keys and tokens must not appear in any span.

Notice what survives. Patterns with a fixed shape, such as email addresses, phone numbers and keys, are easy. Names are not: no pattern separates a person's name from any other words, in English or in Arabic. Finding them is a tagging task, named entity recognition, the same kind of sequence labelling you did in Phase 2. Rules are a floor, not a guarantee.

  


  
6. Habits

  
    
    
  • One JSON object per line. Structured records can be filtered, counted and joined; free-text log messages cannot.
    • 
    
  • Every record carries the trace ID. And return that ID to the user with the answer, so that "it was strange" can become "trace 7f3a was strange".
    • 
    
  • Record versions. Prompt version, model ID, index version. Without them you cannot tell a regression from bad luck.
    • 
    
  • Record failures as failures. An error, a timeout and an empty result are three different facts (Lesson 20).
    • 
    
  • Build the viewer early. A trace nobody can read easily is a trace nobody reads. Even a script that prints an indented list is enough.

Time: 2 hours. No new libraries: a tracer is forty lines.


import contextvars, json, re, time, uuid
from contextlib import contextmanager

_trace = contextvars.ContextVar("trace", default=None)
_parent = contextvars.ContextVar("parent", default=None)
TRACE_FILE = "traces/spans.jsonl"          # create the traces folder first

REDACT = [(re.compile(r"[\w.+-]+@[\w-]+\.[\w.-]+"), "[EMAIL]"),
          (re.compile(r"\+?\d[\d\s-]{7,}\d"), "[PHONE]"),
          (re.compile(r"\bsk-[A-Za-z0-9_-]{8,}"), "[KEY]")]

def redact(value):
    text = value if isinstance(value, str) else json.dumps(value, ensure_ascii=False, default=str)
    for pattern, label in REDACT:
        text = pattern.sub(label, text)
    return text[:4000]                      # bound what one attribute can hold

@contextmanager
def span(name, kind="other", **attrs):
    trace_id = _trace.get() or uuid.uuid4().hex[:12]
    span_id, parent = uuid.uuid4().hex[:8], _parent.get()
    t1, t2 = _trace.set(trace_id), _parent.set(span_id)
    record = {"trace": trace_id, "span": span_id, "parent": parent, "name": name,
              "kind": kind, "start": time.time(), "attrs": dict(attrs)}
    try:
        yield record["attrs"]               # the body may add attributes, e.g. token counts
    except Exception as e:
        record["error"] = repr(e)
        raise
    finally:
        record["end"] = time.time()
        record["attrs"] = {k: v if isinstance(v, (int, float, bool)) else redact(v)
                           for k, v in record["attrs"].items()}      # redact at the moment of storing
        with open(TRACE_FILE, "a", encoding="utf-8") as f:
            f.write(json.dumps(record, ensure_ascii=False, default=str) + "\n")
        _trace.reset(t1); _parent.reset(t2)
