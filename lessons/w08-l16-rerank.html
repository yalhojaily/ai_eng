Reranking and retrieval metrics

Phase 3 taught you never to trust a system you have not measured. Retrieval gets its own eval, with its own metrics, and once you can measure it you can afford a second, slower, much sharper stage.

Answer to last lesson's question. The same three things as in Lesson 9: fixed inputs, known answers, a scoring function. For retrieval the inputs are queries, the known answers are the IDs of the chunks that are relevant to each query, and the scoring function looks at where those IDs appear in the ranked results.

1. An eval set for retrieval

Each item is a query plus the set of chunk IDs a good system should return. Information-retrieval researchers call these relevance judgements, and they have been building such collections since the 1960s. Three practical ways to get yours:

  • From questions to chunks. Write real questions, search by every means you have, and record the chunks that answer each. Slow, and the most faithful to real use.
  • From chunks to questions. Pick a chunk and write a question that it answers. Fast, and you know one relevant chunk for certain. The danger is questions that copy the chunk's wording, which makes word matching look better than it is. Paraphrase on purpose.
  • Generated, then checked. Have a model write questions for sampled chunks, then review them yourself, discarding the vague and the copied. This is Lesson 11's rule again: a model can draft the labels, but a person must validate them.

Include queries in every style and language your users will use, and tag each with its type, so that you can report results per group as in Lesson 9.

2. Four metrics for a ranked list

A retriever returns an ordered list, so its metrics care about position. All are computed at a cut-off k: only the top k results count.

  • Recall@k: of all the relevant chunks, what share appear in the top k?
  • Precision@k: of the top k, what share are relevant?
  • MRR (mean reciprocal rank): 1 divided by the position of the first relevant result, averaged over queries. First place gives 1, second 0.5, tenth 0.1.
  • nDCG@k: rewards relevant results more the higher they are placed, then divides by the best possible score so the result lies between 0 and 1.

3. Which metric to watch

It depends on what consumes the results.

  • A person scanning a results page looks at the top few. MRR and nDCG matter most.
  • A language model reading the top k reads all of them, in any order. What matters first is whether the needed chunk is among them at all: recall@k, at the k you actually pass to the model. A chunk that was not retrieved cannot be used, whatever the model's talents.

For RAG, then, recall@k is the headline number for the first stage. Precision still matters, because irrelevant chunks cost tokens and distract (Lesson 7), and that is what the second stage is for.

4. A sharper tool: the cross-encoder

A bi-encoder compresses the passage into one vector before it has seen the query. Whatever the query turns out to need, the vector was fixed in advance. A cross-encoder instead reads the query and the passage together, as one input, and outputs a single relevance score. Every word of the query can attend to every word of the passage, the mechanism that makes embeddings contextual in Lesson 2. It can notice that not reverses the meaning, or that the passage mentions the right term in the wrong sense.

The catch is in the third row. Nothing can be precomputed, so scoring a million chunks means a million model runs per query.

5. Retrieve, then rerank

So use both, in order. A fast first stage (your hybrid search) narrows the corpus to a shortlist. The cross-encoder then reranks only that shortlist, and the best few go to the model.

Why not rerank everything?

Timings are simple multiplication, assuming pairs are scored one after another and the first stage takes about 30 ms. Real systems batch pairs on a GPU, which changes the constants and not the conclusion.

The two stages have different jobs, and so different metrics. The first stage must not lose the answer: tune it for recall at the shortlist size. The reranker must put the answer on top: judge it by MRR or nDCG at the final cut-off. A reranker can only reorder what it is given. If the right chunk is not in the shortlist, no reranker will find it.

You can also use a general language model as the reranker, asking it to score or order the shortlist. It is slower and costlier per query than a small cross-encoder, and sometimes better. With an eval set you can find out which holds for you.

6. Everything is now a tunable parameter

With a retrieval eval in place, the guesses of the last three lessons become experiments: chunk size, heading prefixes, the normaliser, k1 and b, the fusion constant, the shortlist size, the reranker. Change one, rerun, read the diff (Lesson 12). Two cautions carry over from Phase 3. Tune on a development set of queries and keep a test set back. And look at failures, not only totals: a query whose answer is never retrieved usually points to a chunking or vocabulary problem that no parameter will fix.

Checkpoint

Lab: measure four retrievers

Time: 2 hours, mostly spent writing good queries. Build data/queries.jsonl with 30 queries over your corpus: 15 in English and 15 in Arabic, each with the IDs of its relevant chunks and a type field (term, paraphrase or arabic).

import json
from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/mmarco-mMiniLMv2-L12-H384-v1")   # multilingual

def rerank(query, candidates, top=5):
    scores = reranker.predict([(query, texts[i]) for i in candidates])
    order = sorted(zip(scores, candidates), reverse=True)
    return [i for _, i in order][:top]

def recall_at(ranked_ids, relevant, k):
    return len(set(ranked_ids[:k]) & relevant) / len(relevant)

def reciprocal_rank(ranked_ids, relevant):
    for pos, cid in enumerate(ranked_ids, start=1):
        if cid in relevant:
            return 1 / pos
    return 0.0

queries = [json.loads(l) for l in open("data/queries.jsonl", encoding="utf-8")]
ids = [c["id"] for c in chunks]

systems = {
    "bm25":   lambda q: bm25_search(q, 50),
    "dense":  lambda q: dense_search(q, 50),
    "hybrid": lambda q: rrf([bm25_search(q, 50), dense_search(q, 50)], top=50),
    "hybrid+rerank": lambda q: rerank(q, rrf([bm25_search(q, 50), dense_search(q, 50)], top=50), top=50),
}

for name, fn in systems.items():
    r5 = r20 = mrr = 0
    for q in queries:
        ranked = [ids[i] for i in fn(q["query"])]
        rel = set(q["relevant"])
        r5 += recall_at(ranked, rel, 5); r20 += recall_at(ranked, rel, 20)
        mrr += reciprocal_rank(ranked, rel)
    n = len(queries)
    print(f"{name:14} recall@5 {r5/n:.2f}  recall@20 {r20/n:.2f}  MRR {mrr/n:.2f}")
  1. Fill in the four-row table. Then split it by query type. Where does each system win?
  2. How much does the reranker add to MRR over plain hybrid? How many seconds per query does it cost on your machine?
  3. Find every query whose relevant chunk is missing from the hybrid top 50. For each, write the cause: chunking, vocabulary, language, or a wrong label of your own.
  4. Change one setting from an earlier lesson (chunk size, heading prefix, normaliser) and rerun. Use Lesson 12's flips: which queries were fixed, which broke?
  5. Add this eval to your harness from Phase 3, with a regression gate on recall@20.
