Chunking and indexing a corpus

Before anything can be retrieved, someone has to decide what a "document" is. Cut the text badly and no retriever, however clever, can return a passage that makes sense. This unglamorous step decides more about quality than the choice of model.

Answer to last lesson's question. First, one vector for forty paragraphs is an average of forty topics, so it is close to none of them and paragraph thirty is drowned out. Many embedding models also read only the first few hundred tokens and silently ignore the rest. Second, even if the page is found, you would have to put all forty paragraphs into the prompt to deliver one.

1. Why documents are cut up

A chunk is the unit you embed, store and retrieve. Three pressures make it smaller than a whole document:

  • Focus. An embedding represents one passage's meaning as one point. The more topics the passage covers, the less that point resembles any of them.
  • Limits. Embedding models have a maximum input length. Text beyond it is usually dropped without warning.
  • Budget. Retrieved chunks go into the context window. Small, relevant chunks leave room for more of them and cost less (Lesson 7).

2. Text already has units

Linguists who study text above the sentence, in discourse analysis, observe that writing is organised in nested units: sentences make paragraphs, paragraphs make sections, and each level usually holds one idea at its own scale. A paragraph is, roughly, the writer's own chunk. Cutting along these boundaries keeps ideas whole. Cutting across them gives you the end of one thought glued to the start of another.

Finding even the smallest unit is harder than it looks. Sentence segmentation seems to mean "split at full stops", until you meet abbreviations, decimals and initials. And conventions differ by language: Arabic uses its own comma ، and question mark ؟, and Arabic prose often runs long, linking clauses with و where English would start a new sentence.

3. Three ways to chunk

  • Fixed size. Every N characters or tokens, often with some overlap so that a sentence cut at a boundary appears whole in at least one chunk. Simple, works on anything, respects nothing.
  • Sentence-based. Group whole sentences until a size limit is reached. Never cuts mid-sentence.
  • Structure-based. Split at the document's own boundaries: headings and paragraphs. Best when the source has structure, as Markdown, HTML and well-formatted documents do.

4. How big?

There is no correct size, only a trade-off, and it depends on your questions:

Small chunksLarge chunks
Embeddingsharp, one idea eachblurred across ideas
Standing alonemay lack the context to make senseself-contained
Precision of a hitexactly the relevant linesrelevant lines plus padding
Context budgetmany fitfew fit

Questions with short factual answers favour small chunks. Questions needing explanation favour larger ones. A reasonable starting point for prose is a paragraph or two per chunk. Then stop guessing: chunk size is a parameter, and Lesson 16 gives you the metric to tune it with.

5. Do not strand the chunk

A chunk reading "It is tagged AUX, not VERB." is useless alone. What is? The answer was in the heading two lines above. Three techniques restore what cutting removed:

  • Carry metadata. Store with every chunk its source file, its heading path (POS tags › AUX › Copula) and its position. You need these for citations anyway.
  • Prepend context before embedding. Embed "POS tags › AUX › Copula: It is tagged AUX, not VERB." The vector now knows what "it" refers to. A stronger variant has a model write a one-line description of where the chunk sits in its document, and embeds that along with it.
  • Retrieve small, return big. Match on small chunks for precision, then hand the model the surrounding paragraph or section.

Treat this pipeline like a compiler, and its output like a binary: reproducible from source, never edited by hand. Record what produced it (the corpus version, the chunking settings, the embedding model) because a query must be embedded by the same model as the index, and changing any setting means rebuilding. Give each chunk a stable ID such as file#heading#n; your evaluation data in Lesson 16 will refer to chunks by ID.

Checkpoint

Lab: build the index

Time: 90 minutes. Same corpus as Lesson 13.

import glob, json, re
import numpy as np
from sentence_transformers import SentenceTransformer

def chunk_markdown(path, max_chars=1200):
    """Split at headings, then at paragraphs; keep the heading path with each chunk."""
    text = open(path, encoding="utf-8").read()
    text = re.sub(r"^---.*?---\s*", "", text, flags=re.S)       # drop front matter
    chunks, headings, n = [], [], 0
    for block in re.split(r"\n\s*\n", text):
        block = block.strip()
        if not block:
            continue
        m = re.match(r"(#+)\s+(.*)", block)
        if m:
            level = len(m.group(1))
            headings = headings[:level - 1] + [m.group(2).strip()]
            continue
        for start in range(0, len(block), max_chars):           # very long paragraphs
            n += 1
            chunks.append({
                "id": f"{path}#{n}",
                "path": path,
                "headings": " › ".join(headings),
                "text": block[start:start + max_chars],
            })
    return chunks

chunks = [c for p in sorted(glob.glob("docs/_u-*/*.md")) for c in chunk_markdown(p)]
model = SentenceTransformer("paraphrase-multilingual-MiniLM-L12-v2")
texts = [f'{c["headings"]}: {c["text"]}' for c in chunks]      # context prepended
E = model.encode(texts, normalize_embeddings=True, show_progress_bar=True)

np.save("index/embeddings.npy", E)
with open("index/chunks.jsonl", "w", encoding="utf-8") as f:
    for c in chunks:
        f.write(json.dumps(c, ensure_ascii=False) + "\n")
json.dump({"model": "paraphrase-multilingual-MiniLM-L12-v2", "max_chars": 1200,
           "chunks": len(chunks)}, open("index/meta.json", "w"))
