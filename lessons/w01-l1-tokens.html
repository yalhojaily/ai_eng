From text to tokens

A language model never sees your text. It sees a list of numbers. This lesson is about the step in between, and why that step decides what your application costs, how much it can read, and which languages it handles well.

1. One job: predict the next piece

Strip away the chat window and a large language model does exactly one thing. Given a sequence of pieces of text, it outputs a probability for every piece that could come next. To write a paragraph, the surrounding program picks one piece from that distribution, appends it, and asks again.

text"the cat"
→
tokensthe · cat
→
IDs[1820, 8415]
→
modelP(next)
→
sample"sat"
↺

The IDs above are made up for illustration. Everything else in this course, prompts, retrieval, agents, is a way of arranging the input so that the most probable continuation is the one you want.

You can feel how this works with a model small enough to inspect. The one below was "trained" in your browser by counting, in a few dozen sentences, which word follows which. That is a bigram model: it looks at only one previous word. A real LLM looks at thousands of previous tokens and uses a neural network instead of a count table, but the loop is identical.

2. What counts as a "piece"?

The model needs a fixed list of pieces, its vocabulary, because its output is one probability per entry in that list. So someone has to decide what the entries are. There are three obvious choices, and two of them fail.

UnitVocabularyProblem
WordsMillions, and never completeAny new word, name or typo is unknown. Languages that build long words make it far worse.
CharactersTinySequences become very long, and the model must relearn spelling before it can learn meaning.
SubwordsTens of thousands to a few hundred thousandA compromise: common words are one piece, rare words are assembled from several.

A token is one entry in that subword vocabulary. A common word like the is a single token. A rarer word like tokenization may come out as token + ization. Nothing is ever "unknown", because in the worst case a word is spelled out piece by piece.

Hold this thought. Splitting tokenization into token + ization looks like something a linguist would do. Is the machine doing linguistics? Sometimes, by accident. The next two sections show what linguists mean by a "piece", then how the machine finds its own.

3. The linguist's piece: the morpheme

A morpheme is the smallest unit of language that carries meaning. Cats has two: cat (the animal) and -s (more than one). You cannot split cat further without losing the meaning, so it is one morpheme.

Morphemes that can stand alone are free (cat, read). Those that must attach to something are bound (re-, -ing, -s). Languages differ hugely in how much they pack into one word. English packs little. Arabic, Turkish and Finnish pack a lot: a single Arabic word can be an entire English sentence.

4. The machine's piece: byte-pair encoding

Nobody hands the model a list of morphemes. Its vocabulary is learned from raw text by a simple counting procedure called byte-pair encoding (BPE). It began as a data-compression trick and was adapted for neural translation by Sennrich and colleagues in 2016. Most current LLM tokenizers are variations on it.

The whole algorithm:

  1. Start with every word split into single characters.
  2. Count every adjacent pair of pieces across the whole corpus.
  3. Glue the most frequent pair into one new piece, everywhere it occurs.
  4. Repeat until the vocabulary reaches the size you want.

That is all. No dictionary, no grammar. Frequent sequences become single tokens simply because they are frequent.

    5. Where the two kinds of piece disagree

    In the English preset, BPE found low and est, which are real morphemes. It found them because English mostly builds words by placing morphemes side by side, so a morpheme is also a frequent run of adjacent letters.

    Arabic does not work that way. Much of its vocabulary is built from a root of (usually) three consonants that carries the core meaning, poured into a pattern of vowels and extra letters that carries the grammar. The root letters are not adjacent. Here is the root ك ت ب, to do with writing:

    WordLetters (root in orange)Meaning

    A linguist sees one morpheme, the root, in all six words. BPE can only glue neighbours, so it can never produce a token that means "ك‑ت‑ب with gaps". When you ran the Arabic preset it glued whatever happened to sit together: the unbroken run كت, or a prefix with half a stem (مكت). Meanwhile كاتب, "writer", stayed in single letters, even though it shares its root with words that became one token. Useful for compression, but not the unit of meaning.

    Two more wrinkles. First, production tokenizers usually run BPE on bytes, not letters. In UTF‑8 an English letter is one byte and an Arabic letter is two, so Arabic starts from twice as many units. Second, the merge rules are learned from a corpus that is mostly English, so English sequences earn far more merges. Both push the same way: non-English text tends to shatter into more tokens per word.

    Does that mean the model cannot understand Arabic morphology? No. The network on top of the tokenizer can and does learn that these fragments relate. But it has to spend capacity recovering structure that the tokenizer threw away, and you pay for the extra tokens. Measuring exactly how much is your Phase 1 project.

    6. Why an engineer cares

    Tokens are the unit of account for everything you will build:

    • Cost. Model APIs bill per token, input and output priced separately.
    • Capacity. A model's context window, the most it can read at once, is a number of tokens, not words or pages.
    • Speed. Output is generated one token at a time, so longer answers take proportionally longer.
    • Behaviour. Oddities such as models miscounting the letters in a word come from the model seeing token IDs, not letters.

    A common rule of thumb for English is about four characters, or three quarters of a word, per token. Treat it as a rough guide for one language and one family of tokenizers. For anything that matters, count with the real tokenizer, which is exactly what the lab does.

    Lab: count real tokens

    Time: 30 to 40 minutes. You need: Python 3 and pip install tiktoken, an open-source tokenizer library that runs locally with no API key.

    Before you run anything, write down a prediction: for the same sentence in English and Arabic, which will use more tokens per word, and by roughly what factor?

    import tiktoken

enc = tiktoken.get_encoding("cl100k_base")

samples = {
    "english": "The students will write their lessons in the library.",
    "arabic":  "سيكتب الطلاب دروسهم في المكتبة.",
    "one_word": "وسيكتبونها",
}

for name, text in samples.items():
    ids = enc.encode(text)
    pieces = [enc.decode_single_token_bytes(i).decode("utf-8", errors="replace")
              for i in ids]
    words = len(text.split())
    print(f"{name}: {words} words, {len(ids)} tokens, "
          f"{len(ids) / words:.2f} tokens per word")
    print("  ", pieces)

    Then do these four things:

    1. Compare tokens per word for the two sentences against your prediction.
    2. Look at the Arabic pieces. Some print as �. Using section 5, explain why. (Hint: what unit does the tokenizer cut on?)
    3. Take the token pieces for وسيكتبونها and compare them with the morpheme cuts you made in Try it 2. Does any token boundary match a morpheme boundary?
    4. Add three sentences of your own in each language, of different styles, and check whether the ratio holds.
    Stuck on step 2? Open the explanation

    The tokenizer works on UTF‑8 bytes. An Arabic letter is two bytes, and a token boundary can fall between them. Decoding such a token alone gives half a character, which is not valid text, so Python substitutes the replacement character �. The full sequence still decodes perfectly; only the individual pieces look broken. Keep this script: it is the seed of the tokenizer explorer you ship at the end of Week 2.
