Choosing what goes in the context window

Prompt engineering asks "how do I word this?". Context engineering asks the bigger question: "of everything I could show the model, what should it see for this request?" More is not better, and this lesson shows why.

Answer to last lesson's question. Pasting the complete guidelines into every request makes at least two things worse. Cost and latency rise, since you pay for those pages every time. And accuracy can fall: the few rules that matter for this sentence are buried among hundreds that do not.

1. The context window is a budget

The context is everything the model can see when it produces a token: system prompt, guidelines, examples, documents, conversation history, tool results, and its own answer so far. The context window is the hard limit on all of that together, counted in tokens. Note the last item: the answer shares the window with the input. Fill the window with input and there is no room to reply.

Windows have grown very large, which tempts people to stop thinking and paste everything. Three costs remain however large the window is: you pay per input token, large inputs are slower, and, as section 3 shows, attention is finite even when space is not.

2. This week's linguistics: morphological features

A part-of-speech tag says what class a word is in. Morphological features say what form it is in. Universal Dependencies writes them as Name=Value pairs joined by a bar:

WordMain featuresMeaning
booksNumber=Plurplural
wroteTense=Past|VerbForm=Finfinite past form
كتبتْAspect=Perf|Gender=Fem|Number=Sing|Person=3"she wrote"
المكتبةDefinite=Def|Gender=Fem|Number=Sing"the library"

Languages differ in which features they mark. English nouns mark number and little else. Arabic nouns mark gender, number (with a dual as well as singular and plural), definiteness and case; its verbs agree with their subject in person, gender and number. The complete UD inventory covers features from every language in the project, most of which are irrelevant to any one language.

Here is why this belongs in a lesson about context. Your annotator must now output features, so the model needs the inventory. The whole inventory is long. English input needs a handful of it; Arabic needs a different, larger handful. Which guidelines you include, for which input, is a context-engineering decision, and you will make it in the lab.

3. Why more context can be worse

Two effects are well documented.

Distraction. Irrelevant material is not ignored. Rules about Finnish case endings, sitting in a prompt for English tagging, are still tokens the model attends to, and they can pull its answers off course. Every sentence in a prompt should be there because it changes the output for the better.

Position. Models do not use all parts of a long context equally well. A 2023 study by Liu and colleagues, titled "Lost in the Middle", found that models were best at using information placed at the very beginning or very end of a long input, and noticeably worse at using information in the middle. Models have improved since, but the general lesson stands: where you put something affects whether it is used.

4. Four moves

  • Select. Include only what this request needs. English sentence: English-relevant rules. This is the most powerful move, and Phase 4 automates it with retrieval.
  • Compress. Replace long material with a shorter version that keeps what matters: a summary of earlier conversation, a table in place of paragraphs, twenty lines of rules distilled from twenty pages.
  • Order. Put the most important instructions where they are used best. A common arrangement for long inputs is reference material first and the specific question last, directly before the model starts writing.
  • Structure. Wrap each kind of content in named tags (<guidelines>, <examples>, <sentence>) so the model can tell them apart and you can refer to them by name.

Compression has a price: whatever you cut is gone. A summary of a conversation loses details that may turn out to matter. So compress what is bulky and low-value, and keep verbatim what is short and decisive, such as the exact rule for the copula.

5. A layout that works

[system]  role and task                     short, stable
          <guidelines> selected rules </guidelines>
          <examples> minimal pairs </examples>
[user]    <sentence> the input </sentence>   changes every request
          one-line reminder of the output wanted

Stable material at the top, the changing input at the bottom, and a brief restatement of the task right at the end, where it is freshest when generation begins.

6. A bonus for keeping the top stable

Many providers offer prompt caching: if the beginning of your request is identical to a recent one, that repeated prefix is processed more cheaply and faster. The details and discounts vary by provider and model. The design rule is the same everywhere and matches the layout above: put what never changes first, and what changes every time last. One changed character near the top invalidates everything after it.
