Prompt chains and validation

One model call is a function. Real applications are programs made of several, with ordinary code between them checking each result. This lesson is about that code as much as the prompts.

Answer to last lesson's question. 0.9 × 0.9 × 0.9 × 0.9 = 0.66. Four things done 90% right, independently, leave only about two words in three fully correct. Each part looked fine; the whole does not. That arithmetic governs everything in this lesson.

1. Errors multiply

In a chain, each step works on the output of the one before. A wrong segmentation cannot be rescued by perfect tagging: the tagger is tagging the wrong units. So, roughly, the accuracy of the whole is the product of the accuracies of the steps.

That sounds like an argument against chains. It is really an argument for gates: checks between steps that catch a bad result and send it back before it travels further. A gate turns a silent error into a retry.

Experiments. At 95% per step, how many steps until the chain is below 75%? Now set the gate to catch 80% of errors. The model assumes one retry per caught error, with the same chance of success as the first attempt.

2. Linguists have always worked in chains

Long before language models, natural language processing was organised as a pipeline, each stage feeding the next:

tokenisefind words
→
segmentsplit clitics
→
tagPOS, features
→
lemmatisedictionary form
→
parsestructure

The order is not arbitrary. You cannot tag a unit you have not identified, and you cannot find the lemma of saw until you know whether it is a verb. Each stage also had its own measured accuracy, and the field knew the multiplication problem well: it was called error propagation or cascading errors.

A large language model can attempt the whole pipeline in one call. Whether it should is an engineering question with a measurable answer, and you will measure it in the lab.

3. Gates: check with code, not with hope

A gate is an ordinary function that inspects a step's output and returns either "fine" or a description of what is wrong. The best gates test invariants: properties that must hold for any correct answer, whatever the input.

StepInvariant a program can check
SegmentThe units, joined together, equal the original word exactly. No unit is empty.
TagOne entry per unit, in the same order, with the same forms. Every tag is in the tagset.
FeaturesEvery feature name and value is in the allowed inventory. A VERB has no Definite.
LemmaNot empty. Contains no spaces.

Notice what these are: cheap, exact, and written once. A code check costs nothing per run and is never wrong about what it checks. Use a model to judge output only for properties code cannot test.

4. Retry with feedback

When a gate fails, do not simply call again and hope. Tell the model what was wrong, in the gate's own words, and ask again. The error message is new information.

Three rules keep retries safe. Cap them: one or two attempts, then stop. Fail loudly: when the cap is reached, raise an error or mark the item for a person; never pass a known-bad result downstream. Count them: a step that needs retries on a fifth of its inputs has a prompt problem that retries are hiding.

5. Four shapes a chain can take

  • Sequential. A then B then C, each using the last one's output. The pipeline above.
  • Routing. A cheap first step classifies the input, and code sends it to a specialised prompt. Arabic goes to the Arabic guidelines, English to the English ones.
  • Parallel. Run several calls at once and combine: split a document into sentences and tag them simultaneously, or ask the same hard question three times and take the majority answer.
  • Generator and critic. One call produces, a second reviews against explicit criteria, and the first revises. Useful when "good" can be described but not checked by code.

6. When not to chain

Every extra call adds latency and cost, and every boundary is a place where context is lost: step 2 knows only what step 1 passed on. A tagger that receives bare units, without the sentence they came from, has lost the context that decides between ذهب the verb and ذهب the noun.

So the working rule is: start with one call. Split only where you can name the failure that splitting fixes, and can measure that it did. When you do split, pass forward everything the next step needs, not only the previous step's output.

Checkpoint

Lab: a gated chain for Arabic

Time: 90 minutes. Build a two-step chain with gates, then compare it with your single-call annotator on the Arabic half of your gold standard.

def call_json(system, user, schema, name):
    r = client.chat.completions.create(
        model=MODEL, temperature=0,
        messages=[{"role": "system", "content": system},
                  {"role": "user", "content": user}],
        response_format={"type": "json_schema",
                         "json_schema": {"name": name, "strict": True, "schema": schema}},
    )
    return json.loads(r.choices[0].message.content)

SEG_SCHEMA = {"type": "object",
              "properties": {"units": {"type": "array", "items": {"type": "string"}}},
              "required": ["units"], "additionalProperties": False}

def check_segments(word, units):
    """Return None if fine, otherwise a sentence describing the problem."""
    if not units or any(u == "" for u in units):
        return "there is an empty unit"
    if "".join(units) != word:
        return "the units joined together must equal the original word exactly, letter for letter"
    return None

STATS = {"calls": 0, "retries": 0, "failures": 0}

def segment(word, sentence, max_retries=1):
    user = f"<sentence>{sentence}</sentence>\n<word>{word}</word>"
    for attempt in range(max_retries + 1):
        STATS["calls"] += 1
        units = call_json(SEG_SYSTEM, user, SEG_SCHEMA, "segments")["units"]
        problem = check_segments(word, units)
        if problem is None:
            return units
        STATS["retries"] += 1
        user += f"\nYour previous answer {units} was rejected: {problem}. Answer again."
    STATS["failures"] += 1
    raise ValueError(f"could not segment {word!r}")
  1. Write SEG_SYSTEM: a full briefing for splitting an Arabic written word into its syntactic words, with two or three minimal-pair examples. Note that the sentence is passed along as context.
  2. Write step 2, tag(units, sentence), with its own gate: same number of entries, same forms in the same order, every tag in the tagset.
  3. Run the chain on your 10 Arabic gold sentences. Record fully-correct words, total calls, retries, failures and elapsed time.
  4. Run your single-call annotator from Lesson 7 on the same sentences. Same measurements.
  5. Which is more accurate, and what did the difference cost in calls and seconds? Would routing (chain for Arabic, single call for English) get the best of both?
  6. Look at the words the gates passed but your gold standard says are wrong. What kind of mistake gets through?

Reading duties

Phase 2 project: ship the linguistic annotator

Assemble the four labs into one tool: given a sentence in English or Arabic, return a validated annotation of every syntactic word.

What to build

  1. A command-line program: sentence in, JSON out, with form, lemma, upos and feats for each syntactic word.
  2. Prompts kept in their own files, not buried in code, with PROMPT_LOG.md recording each version and its error count.
  3. Routing by language, with selected guidelines for each.
  4. Gates after every model call, a retry cap, and a loud failure when the cap is hit.
  5. A --stats option printing calls, retries, input and output tokens for the run.
