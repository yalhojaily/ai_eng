Guardrails and deployment

The last step turns a program you run into a service others call. Nothing about the model changes. Everything around it does: who sends the input, how long they will wait, what happens when it fails, and how you replace it with a better version without breaking what works.

Answer to last lesson's question. The input is no longer yours: it may be long, malformed, hostile, or in a language you never tested. Many requests arrive at once. Callers wait at the other end of a network and give up, or retry, when a run takes minutes. Your API key is spent by people you have never met. Failures happen while you are asleep. And you can no longer fix things by editing a file and rerunning, because other people depend on the version that is live.

1. From script to service

An agent run takes tens of seconds to minutes. An ordinary web request is expected back in a second or two, and proxies along the way cut connections that stay silent for long. So the standard shape for slow work is a job:

POST /reportsreturns a job ID at once
→
workerruns the agent
→
GET /reports/{id}status, then result

The caller submits, gets an ID immediately, and asks for status until the job is done. The alternative, when a person is watching, is to hold the connection open and stream progress events as in Lesson 3. Either way, a few properties make the service sturdy:

  • Timeouts everywhere. On each model call, each tool call and the job as a whole. A call with no timeout will, one day, wait forever.
  • Bounded concurrency. A fixed number of jobs at once, the rest queued. Your provider's rate limits and your own budget (Lesson 27) are both finite.
  • Idempotent submission. Callers retry. If the same request arrives twice with the same client-supplied key, return the existing job; do not run and bill it twice.
  • Pinned configuration. Model ID, prompt version and index version come from one versioned config file, are recorded in every trace (Lesson 25), and change only through a release.
  • Secrets outside the code. Environment variables or a secret store. Never the repository, never a log.

2. Three places for guardrails

A guardrail is a check, outside the model, that stops or alters something before harm is done. They sit at three points:

WhereChecksYou already have
Inputsize and format limits, allowed languages, scope ("is this a question this service answers?"), policy filtersschema validation (Lesson 4)
Outputschema, citation and evidence verification, removal of personal data, policy filtersgates and verifiers (Lessons 8, 17, 23)
Actionallow-lists of tools and arguments, limits on what can be written or sent, human approval for anything irreversibleleast privilege (Lesson 22)

Two design rules. Prefer guardrails that are code: they are fast, free, and behave the same every time. Use a model as a guardrail only for what code cannot judge, and then treat it as a classifier with a measured error rate, like any judge (Lesson 11). And decide for each guardrail whether it fails closed, blocking the request when the check itself breaks, or fails open, letting it through. Safety checks should fail closed. Conveniences can fail open.

3. Why filters on text are so easy to slip past

The simplest input guardrail is a list of forbidden words. Suppose your service must decline questions about salaries, a topic outside its remit. Block the string salary and you are done? Writing systems give an evader a great deal of room, because many different sequences of characters look or read the same to a person:

  • Spacing and punctuation inside the word.
  • Substituted characters: digits for letters, or letters from another alphabet that look identical. Cyrillic а and Latin a are different characters with the same shape. Such pairs are called homoglyphs.
  • Invisible characters: zero-width spaces and joiners that display as nothing.
  • Optional marks: in Arabic, vowel marks and the stretching character can be sprinkled through a word without changing how it reads, as you saw in Lesson 15.

The durable protection is Lesson 22's: limit what the system is able to do.

4. Most difficult inputs are not hostile, only unclear

Far more requests go wrong through ambiguity than through attack. Linguists sort ambiguity into kinds, and each calls for a slightly different response:

  • Lexical: a word has several senses. "How is 'light' used?" The noun, the adjective, the verb?
  • Structural: the words can be grouped in more than one way. "Compare run and walk in news and fiction": two words in each of two genres, or run in news against walk in fiction?
  • Referential: it is unclear what an expression points to. "Do the same for the other one."
  • Scope of the request: how much is wanted. "Tell me about 'issue'." A line, or a ten-page report costing a dollar?

A service has three options: ask, guess silently, or guess and say so. For cheap, reversible requests the third is usually best: proceed on the most likely reading and state the assumption at the top of the answer, so that a wrong guess is visible and cheap to correct. Ask first when the readings differ greatly in cost or cannot be undone.

5. Failing well

Model providers return errors as a matter of course: rate limits, overloads, timeouts. Most are transient, so the standard response is to retry with exponential backoff: wait a little, then twice as long, then twice that. Add jitter, a random variation in each wait, so that a thousand clients that failed together do not all retry at the same instant and cause the next failure themselves.

Try it · 3

Plan the retries

Experiments. Set the multiplier to 1: fixed waits. How long does a caller wait in total with the multiplier at 2 and eight retries? Is that acceptable for someone watching a screen? For an overnight batch? The cap of 60 seconds per wait keeps the schedule from running away.

Retry only what is safe to repeat, and only errors that are transient: a malformed request will fail identically every time. Cap the attempts. When retries are exhausted, fail clearly, keep the trace, and tell the caller something true: what happened, whether trying again later might help, and the trace ID.

6. Rolling out a change

Lesson 12 gave you a gate before release. Production needs caution after it too, because your eval set is a sample and real traffic always contains something it lacks.

  1. Offline gate. The harness passes: no regression on the development set, test set checked.
  2. Shadow. The new version runs on a copy of live requests. Its answers are recorded and compared with the current version's, and never shown to users. Free of risk, and it meets real inputs.
  3. Canary. A small share of real traffic, say five percent, is served by the new version, while Lesson 26's signals are watched for both groups side by side.
  4. Full release, with the previous version kept ready.
  5. Rollback on any alarm: one configuration change, practised in advance, that restores the last version.

Because model ID, prompt and index are pinned in one config (section 1), a "version" is a single file, and rolling back is replacing it. And when something does go wrong in production, the loop you have been building since Phase 3 closes: find the trace, reproduce it, add it to the eval set, fix, pass the gate, release in stages.

Lab: put the agent behind an API

Time: 3 hours. pip install fastapi uvicorn.

# service.py     run with: uvicorn service:app
import json, re, unicodedata, uuid, asyncio
from fastapi import FastAPI, HTTPException
from pydantic import BaseModel

CONFIG = json.load(open("config/release.json"))     # model, prompt_version, index_version, limits
app = FastAPI()
JOBS = {}                                            # job id → {"status", "result", "trace"}
SLOTS = asyncio.Semaphore(CONFIG["max_concurrent_jobs"])

class ReportRequest(BaseModel):
    word: str
    idempotency_key: str | None = None

ZERO_WIDTH = re.compile(r"[​-‍⁠﻿]")

def clean_word(raw):
    """Input guardrail. Returns the normalised word, or raises with a reason."""
    w = ZERO_WIDTH.sub("", unicodedata.normalize("NFKC", raw)).strip().lower()
    if not 1 <= len(w) <= 40:
        raise ValueError("The word must be between 1 and 40 characters.")
    if not re.fullmatch(r"[a-z][a-z'-]*", w):
        raise ValueError("This service covers single English words written in Latin letters.")
    return w

async def run_job(job_id, word):
    async with SLOTS:                                # at most N agent runs at once
        JOBS[job_id]["status"] = "running"
        try:
            report, trace_id = await asyncio.wait_for(
                asyncio.to_thread(research_word, word, CONFIG),      # your agent, with tracing
                timeout=CONFIG["job_timeout_seconds"])
            JOBS[job_id].update(status="done", result=report, trace=trace_id)
        except asyncio.TimeoutError:
            JOBS[job_id].update(status="failed", result="The run exceeded its time limit.")
        except Exception as e:
            JOBS[job_id].update(status="failed", result=f"The run failed: {type(e).__name__}.")

@app.post("/reports", status_code=202)
async def submit(req: ReportRequest):
    try:
        word = clean_word(req.word)
    except ValueError as e:
        raise HTTPException(status_code=422, detail=str(e))
    job_id = req.idempotency_key or uuid.uuid4().hex[:12]
    if job_id not in JOBS:                           # a retried submission returns the same job
        JOBS[job_id] = {"status": "queued", "result": None, "trace": None}
        asyncio.create_task(run_job(job_id, word))
    return {"job": job_id, "status": JOBS[job_id]["status"]}

@app.get("/reports/{job_id}")
async def status(job_id: str):
    if job_id not in JOBS:
        raise HTTPException(status_code=404, detail="No such job.")
    return JOBS[job_id]

@app.get("/health")
async def health():
    return {"ok": True, "release": CONFIG["release"], "model": CONFIG["model"]}
  1. Write config/release.json and research_word(word, config), which runs the full agent from Lesson 23 with tracing, caches and budgets, and returns the verified report and its trace ID.
  2. Start the service. Submit a word, poll until done, and fetch the report. Then use the trace ID to display the run with show_trace.
  3. Submit the same request twice with one idempotency key. Confirm from the traces that the agent ran once.
  4. Attack your own input guardrail: an empty string, a ten-thousand-character string, a word with a zero-width space inside, a word in Cyrillic look-alikes, a whole instruction sentence. What gets through that should not, and what is refused that should not be?
  5. Submit ten words at once. Check that no more than your configured number run concurrently, and that none is lost.
  6. Add retry with backoff and jitter around the model call, for rate-limit and overload errors only. Simulate three failures in a row and watch the waits in the trace.
  7. Shadow a new release. Create a second config with a different prompt version or model. For each request, also run the shadow config in the background, store both reports, and after twenty requests compare them with Lesson 24's metrics. Would you promote it?
  8. Point Lesson 24's eval at the service's HTTP endpoint instead of the Python function. The same twenty tasks should pass.

Reading duties

Phase 6 project: run the agent as a service

The corpus research agent, deployed: other people can call it, you can see what it does, you know what it costs, and you can change it safely.

What to build

  1. The API from this lab: job submission, status, health, idempotency, bounded concurrency, timeouts.
  2. Tracing on every span, with redaction, and a command to display any trace by ID.
  3. A daily metrics table from the traces: volume, p50 and p95 latency, tokens and cost per request, verifier failure rate, one input-drift signal, and one alert rule.
  4. Tool-result and response caches keyed by versions; a cascade behind the verifier; per-request and daily budgets with a degraded mode.
  5. Input and output guardrails, and retries with backoff.
  6. One pinned release config, and a shadow-run comparison of a second.
  7. It may run on your own machine. If you put it on a public address, add an access key and the per-user limits first.
