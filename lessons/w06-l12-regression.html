Regression-testing prompts like code

You already know how to keep software from breaking: tests that run on every change. A prompt is part of your program's behaviour, so it gets the same treatment. This lesson turns your eval into a habit that runs itself.

1. A prompt is code without a compiler

Change a line of ordinary code and a type checker, a test suite and a reviewer stand between you and production. Change a line of a prompt and, by default, nothing does. The edit that fixes today's complaint can quietly undo last month's fix, and you find out from a user.

A change that breaks something that used to work is a regression. Regression testing means rerunning a fixed set of cases after every change and comparing with the last known-good result. For prompts that requires exactly what you have built in this phase, plus three engineering habits: prompts live in version control, every change runs the eval, and results are stored so that versions can be compared.

2. Read the diff, not the average

An average compresses hundreds of outcomes into one number. Two versions with the same accuracy can be right about quite different items. The useful view is the list of items whose outcome changed: those fixed (wrong before, right now) and those broken (right before, wrong now).

3. Is the difference real?

Lesson 9's confidence intervals compare two numbers as if they came from different samples. When both versions ran on the same items you can do much better, because most items come out the same either way and tell you nothing. Only the flips carry information.

The reasoning is short. If the change truly made no difference, each flip would be as likely to be a fix as a break, like a coin toss. So ask: with this many flips in total, how surprising is a split this uneven? That is the sign test (a close relative is called McNemar's test). The result is a p-value: the probability of a split at least this lopsided arising by chance. Small means the change probably did something.

Try it · 2

Count the flips

Experiments. Start with last lesson's 12 and 10. Then try 12 and 2. Then 3 and 0: three fixes and no breaks feels decisive, but is it? The conventional line for "probably real" is p below 0.05, which is a convention, not a law of nature.

Statistics answers "is it real?". It does not answer "is it acceptable?". A change that is significantly better overall and breaks ten cases your users rely on may still be the wrong change. Read the broken list.

4. Anatomy of a harness

project/
  prompts/annotate_v7.txt        one file per version, in git
  data/en_dev.jsonl  ar_dev.jsonl  en_test.jsonl  ar_test.jsonl
  evals/run.py                   prompt + dataset  →  results/<name>.json
  evals/compare.py               two result files  →  table, flips, p-value
  evals/test_regression.py       the gate
  results/                       one file per run, kept

Four properties make a harness something you will actually run:

  • Cached. Store each model response under a key made from the model name, the prompt and the input. Rerunning after a change to the scorer then costs nothing, and only items affected by a prompt change are sent again.
  • Repeatable. Temperature 0, fixed sampling seed for the data, model ID written into the result file. A score you cannot reproduce is an anecdote.
  • Per-item results. Save the outcome of every item, not only the totals. Diffs and error analysis need them.
  • Cost and time recorded. Tokens and seconds are results too. A prompt that gains a point and doubles the bill is a trade-off to see, not to discover later.

5. Gates: let the machine say no

Once results are files, a short test can compare a candidate with the stored baseline and fail when a limit is crossed. Wire that into your normal test command and a bad prompt change is blocked exactly as a failing unit test is. What goes in the gate is a policy decision about your product.

Try it · 3

Set the policy

Three changes are waiting to ship. Set your limits and see which get through. The baseline scores 88.0%.

There is no setting that is simply correct. Is a 40% saving worth 0.8 points? Is one more point worth a third more cost? The gate does not make that judgement for you. It makes sure the judgement is made once, on purpose, and then applied every time.

6. Keeping the eval alive

Every failure becomes a test. When a user reports a wrong answer, add that input and its correct output to the dataset before fixing the prompt. The set grows toward the cases that matter, and the bug cannot return silently.

Model changes are prompt changes. Providers retire models and release new ones. A prompt tuned on one model can behave differently on its successor. With a harness, evaluating a new model is one command and a diff. Without one, it is a leap.

Version the data too. Treebanks are released in numbered versions, with corrections in each release, and a score on one version is not comparable with a score on another. Your own gold standard changes as you fix its mistakes. Record the dataset version in every result file.

Protect the test set. All of this daily running happens on the development set. The held-out test set from Lesson 9 comes out before a release, not before lunch.

Lab: build the harness

Time: 2 hours. Assemble the pieces from Lessons 9 to 11 into the layout in section 4.

# evals/common.py
import hashlib, json, os
from math import comb

CACHE_PATH = "results/cache.json"
cache = json.load(open(CACHE_PATH, encoding="utf-8")) if os.path.exists(CACHE_PATH) else {}

def cached(model, system, text, fn):
    key = hashlib.sha256(json.dumps([model, system, text]).encode()).hexdigest()
    if key not in cache:
        cache[key] = fn(text, system)
        json.dump(cache, open(CACHE_PATH, "w", encoding="utf-8"), ensure_ascii=False)
    return cache[key]

def flips(base, cand):
    """base, cand: dicts of item id → True/False (correct or not)"""
    fixed = [k for k in base if not base[k] and cand.get(k)]
    broken = [k for k in base if base[k] and not cand.get(k)]
    return fixed, broken

def sign_test(fixed, broken):
    n, k = fixed + broken, min(fixed, broken)
    if n == 0:
        return 1.0
    return min(1.0, 2 * sum(comb(n, i) for i in range(k + 1)) / 2 ** n)
# evals/test_regression.py     run with: pytest evals/
import json
from common import flips

def test_candidate_is_safe():
    base = json.load(open("results/baseline.json"))
    cand = json.load(open("results/candidate.json"))
    fixed, broken = flips(base["items"], cand["items"])
    assert cand["schema_failures"] == 0
    assert cand["accuracy"] >= base["accuracy"] - 0.005
    assert len(broken) <= 5, f"broke: {broken[:10]}"
    assert cand["input_tokens"] <= base["input_tokens"] * 1.10
