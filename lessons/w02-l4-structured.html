Structured output and tool calling

1. Programs cannot read prose

Last lesson's question: you ask for the part of speech of a word and need exactly one tag back. The obvious approach is to ask nicely and then pull the tag out of the reply with string handling. Try it against replies of the kind models actually give.

Pick a parsing strategy

Notice: every text strategy fails somewhere, and each fix breaks a different case. The JSON strategy is perfect on the replies that are JSON and useless on the rest. So the real task is not better parsing. It is making every reply look like the last row.

2. Say what shape you want: schemas

Linguists solved a version of this problem long ago. When many people annotate a corpus, free-form labels are useless: one writes verb, another V, a third action word. So annotation projects define a tagset, a closed list of permitted labels, and guidelines for applying them. The Universal Dependencies project, which you will use for evaluation in Phase 3, defines exactly 17 universal part-of-speech tags (NOUN, VERB, ADJ, ADP, …) used across more than a hundred languages.

A tagset is a schema. In software the standard way to write one down is JSON Schema: a JSON document that describes what another JSON document must look like. The pieces you need most:

  • type: object, array, string, number, boolean.
  • properties and required: which fields exist, and which must be present.
  • enum: a closed list of allowed values. This is your tagset.
  • additionalProperties: false: no fields beyond those listed.

3. Three levels of enforcement

  

    
LevelWhat you doWhat you get

    
1. AskDescribe the format in the promptUsually right. Sometimes wrapped in prose or code fences.

    
2. JSON moderesponse_format: {"type": "json_object"}Valid JSON, but in whatever shape the model chose.

    
3. Structured outputsresponse_format of type json_schema, with your schemaJSON that matches your schema, on models and providers that support it.

  

  
Level 3 is not a stronger request. It works by a different mechanism, and you already know the parts. At every step the model produces a probability for every token. With constrained decoding, the server checks which tokens could legally come next under your schema, sets the probability of all the others to zero, and samples from what remains. The model cannot emit "verb" in lowercase if the enum says "VERB", because that token is never on offer.

And a constrained model is still the same model: if it "wanted" to write an explanation and you forced a bare tag, you get its best tag, not a better-reasoned one.


  
4. Valid is not the same as correct

  
A schema checks form. It cannot check truth. {"upos": "NOUN"} for book in "Book a flight" is flawless JSON and a wrong answer. Keep two separate questions in your head for the rest of this course:

  
    
    
  • Is the output well-formed? Schemas and validation answer this, cheaply, on every request.
    • 
    
  • Is the output right? Only evaluation against known answers can tell you. That is all of Phase 3.
    • 
  

  
Even with structured outputs, validate in your own code. The pattern is short: parse, validate, and if either fails, retry once with the error message included, then give up loudly. Never pass unvalidated model output to the next stage.


  
5. Tools: letting the model ask for things

  
A model can only produce tokens. It cannot count the tokens in a string, search a corpus, read a file or know today's date. Tool calling is structured output put to work: you describe functions the model may request, and when it wants one, it emits a structured request instead of an answer.

  
The crucial point: the model never runs anything. It writes a request. Your code decides whether to honour it, runs the function, and sends the result back as another message. Then the model continues.

    "description": "Count how many tokens a text uses. Use this whenever the user asks about token counts; never estimate.",
    "parameters": {
      "type": "object",
      "properties": {
        "text": { "type": "string", "description": "The exact text to count." }
      },
      "required": ["text"]
    }
  }

6. Design rules

  
    
    
  • Descriptions are prompts. The model chooses tools by reading their names and descriptions. Say when to use the tool, not only what it does.
    • 
    
  • Prefer enums to free strings wherever the set of answers is closed. A tagset beats a text field.
    • 
    
  • Arguments are untrusted input. The model wrote them, possibly influenced by text it read. Validate them as you would validate a web form before touching a file or a database.
    • 
    
  • Structured output or tool? Use structured output when you want data back. Use a tool when the model needs something done or something looked up before it can answer.
    • 
    
  • Order fields so thinking comes first. Output is generated left to right. A reason field placed before upos lets the model reason before committing; placed after, it is a justification written after the fact.
    •

Part A. Schema-constrained annotation.


import json, jsonschema

UPOS = ["ADJ","ADP","ADV","AUX","CCONJ","DET","INTJ","NOUN","NUM",
        "PART","PRON","PROPN","PUNCT","SCONJ","SYM","VERB","X"]

schema = {
    "type": "object",
    "properties": {
        "tokens": {
            "type": "array",
            "items": {
                "type": "object",
                "properties": {
                    "form":  {"type": "string", "description": "The word as written"},
                    "lemma": {"type": "string", "description": "Dictionary form"},
                    "upos":  {"type": "string", "enum": UPOS},
                },
                "required": ["form", "lemma", "upos"],
                "additionalProperties": False,
            },
        }
    },
    "required": ["tokens"],
    "additionalProperties": False,
}

def annotate(sentence):
    r = client.chat.completions.create(
        model=MODEL,
        temperature=0,
        messages=[
            {"role": "system", "content": "Annotate each word of the sentence with its "
             "lemma and Universal Dependencies part-of-speech tag."},
            {"role": "user", "content": sentence},
        ],
        response_format={"type": "json_schema",
                         "json_schema": {"name": "annotation", "strict": True, "schema": schema}},
    )
    data = json.loads(r.choices[0].message.content)
    jsonschema.validate(data, schema)      # never skip this
    return data["tokens"]

for t in annotate("Book a flight and read the book."):
    print(t)

  
    
    
  1. Does it tag the two occurrences of book differently? That is contextual meaning from Lesson 2, visible in output.

Part B. The tool loop.


import tiktoken
enc = tiktoken.get_encoding("cl100k_base")

def count_tokens(text):
    return {"tokens": len(enc.encode(text)), "words": len(text.split())}

tools = [{
    "type": "function",
    "function": {
        "name": "count_tokens",
        "description": "Count tokens and words in a text. Use whenever token counts "
                       "are needed; never estimate them.",
        "parameters": {
            "type": "object",
            "properties": {"text": {"type": "string", "description": "Exact text to count"}},
            "required": ["text"],
        },
    },
}]

messages = [{"role": "user", "content":
    "Which costs more tokens per word: 'The students will write their lessons "
    "in the library.' or its Arabic translation? Translate it, then measure both."}]

while True:
    r = client.chat.completions.create(model=MODEL, messages=messages, tools=tools)
    msg = r.choices[0].message
    messages.append(msg)
    if not msg.tool_calls:
        break
    for call in msg.tool_calls:
        args = json.loads(call.function.arguments)
        print("model asked for:", call.function.name, args)
        result = count_tokens(**args)
        messages.append({"role": "tool", "tool_call_id": call.id,
                         "content": json.dumps(result)})

print(msg.content)

  
    
    
  1. How many requests did the loop make? Did the model call the tool twice in one turn or across two turns?
    2. 
    
  2. Delete the sentence "never estimate them" from the description, and change the question to ask for a "rough" comparison. Does the model still call the tool? This is what "descriptions are prompts" means in practice.
    3. 
    
  3. The numbers come from cl100k_base, which may not be your model's own tokenizer. How could you check, using what you measured in Lesson 3's lab?
    4.
