Model-graded evals and their traps

Tags can be checked by comparing strings. Explanations, summaries and translations cannot. For those, the common answer is to have a second model do the grading. It works, on one condition: you treat the grader as one more annotator whose reliability has to be measured.

By the end you can

  • Choose between code checks, reference comparison, human review and a model judge.
  • Write a rubric specific enough that two graders reach the same verdict.
  • Compute Cohen's kappa and explain why raw agreement overstates reliability.
  • Name the common biases of model judges and test for them.
Answer to last lesson's question. You cannot compare a free-text note with a single right answer, because many different sentences would be good. You need a grader that applies criteria. People are the reference graders but do not scale to a thousand notes on every prompt change. A model can, if you first check it against people.

1. Four ways to grade, cheapest first

MethodGood forWeakness
Code checksformat, length, required words, exact answers, invariantscannot judge meaning
Reference comparisonoutput should resemble a known good answer: word overlap or embedding similaritymany good answers look unlike the reference; similarity is not correctness (recall "safe" and "not safe" in Lesson 2)
Model judgeopen-ended quality against written criteria, at scalehas biases; must be validated
Human reviewthe standard everything else is checked againstslow, costly, and people disagree too

Use the cheapest method that can actually measure the property. A note's length is a code check. Whether it identifies the right sense of the word needs a judge. Mixing several is normal: code checks first, a judge only for what is left.

2. A model as judge

A model judge (often written "LLM-as-judge") is a prompt that receives the input, the output to be graded, and a rubric, and returns a verdict. It is the structured-output pattern from Lesson 4 pointed at another model's work. Design choices that make judges more reliable:

  • Reasoning before verdict. Put a reasoning field ahead of the verdict field, so the judgement is formed before it is committed (Lesson 6).
  • Pass or fail, not one to ten. Coarse scales are far more consistent. Nobody, human or model, can say reliably what separates a 6 from a 7.
  • One criterion per call. "Is the sense right?" and "Is it one sentence?" are separate questions. Bundled together, one leaks into the other.
  • Show graded examples. A few passes and fails with reasons, including borderline ones.
  • Prefer a different model from the one being graded, where you can.

3. Rubrics are annotation guidelines

A rubric is what Lesson 9 called guidelines, written for a grader. The test is the same as for any prompt: could two careful people apply it independently and reach the same verdict? "Is the note good?" fails that test. This passes:

PASS only if all three hold:
 (a) the note states the sense the word has in THIS sentence;
 (b) the note is exactly one sentence;
 (c) the note contains no false statement about the language.
Otherwise FAIL. Do not reward extra detail. Do not require
anything the three criteria do not mention.

Now be an annotator yourself. Grade eight notes with that rubric. Afterwards you will see how a model judge graded the same eight.

4. Measuring agreement: Cohen's kappa

You and the judge agreed on some share of the items. Is that share good? Corpus linguists learned long ago that raw agreement flatters. If nine outputs in ten deserve a pass, two graders who each say "pass" nine times in ten without looking will still agree most of the time, by chance alone.

Cohen's kappa corrects for this. It asks how much of the room above chance agreement the two graders actually filled:

kappa = (observed agreement − chance agreement) / (1 − chance agreement)

Kappa is 1 for perfect agreement, 0 for agreement no better than chance, and negative when graders disagree more than chance would. By a widely used rule of thumb, above 0.8 is strong, 0.6 to 0.8 is substantial, 0.4 to 0.6 is moderate, and below 0.4 the grading is not yet dependable. Treat those bands as rough guidance, not law.

5. The traps

Model judges have characteristic biases, documented across many studies:

  • Verbosity bias. Longer, more detailed answers get better marks, whether or not the rubric asks for detail. You may have just seen this.
  • Position bias. Asked to choose between answer A and answer B, judges favour one position. Run every comparison twice with the order swapped, and count only verdicts that survive the swap.
  • Self-preference. Judges tend to rate text from their own model family more kindly.
  • Leniency. Left to themselves, judges pass too much. A judge that passes everything has high agreement and no value.
  • Criteria drift. Judges add requirements you never wrote, or forgive ones you did.

None of these makes judges useless. Each one is a reason the judge must be measured against human labels before its numbers are believed, and measured again whenever its prompt or model changes.

6. The process that works

  1. Label by hand first. Grade 50 to 100 real outputs yourself against a written rubric. Doing this is how you discover what the rubric should say.
  2. Write the judge from the rubric and a few of those labelled examples.
  3. Measure the judge on the remaining labelled items: agreement, kappa, and its own confusion matrix. Which way does it err: passing failures, or failing passes?
  4. Fix the rubric, not only the judge prompt. Disagreement usually means the criteria were ambiguous for you too.
  5. Deploy, and keep checking. Hand-grade a small random sample from every large run.

A judge validated this way is an instrument. One that was never compared with a person is a second opinion from a stranger.

Checkpoint

Lab: build and validate a judge

Time: 90 minutes. Extend your annotator so that for one chosen word in a sentence it writes a one-sentence note for a learner. Generate notes for 40 word-in-sentence pairs (20 English, 20 Arabic), choosing ambiguous words such as that, to, can, book, ذهب.

JUDGE_SCHEMA = {
    "type": "object",
    "properties": {
        "reasoning": {"type": "string"},
        "verdict": {"type": "string", "enum": ["PASS", "FAIL"]},
    },
    "required": ["reasoning", "verdict"],
    "additionalProperties": False,
}

JUDGE_SYSTEM = """You grade notes written for language learners.
... your rubric, and three graded examples with reasons ...
"""

def judge(sentence, word, note):
    user = (f"<sentence>{sentence}</sentence>\n<word>{word}</word>\n"
            f"<note>{note}</note>")
    return call_json(JUDGE_SYSTEM, user, JUDGE_SCHEMA, "grade")["verdict"]

def kappa(a, b):
    """a, b: equal-length lists of 'PASS' / 'FAIL'"""
    n = len(a)
    observed = sum(x == y for x, y in zip(a, b)) / n
    pa, pb = a.count("PASS") / n, b.count("PASS") / n
    chance = pa * pb + (1 - pa) * (1 - pb)
    return (observed - chance) / (1 - chance) if chance < 1 else 1.0
  1. Grade all 40 notes yourself, PASS or FAIL, before writing the judge. Save your labels to a file.
  2. Write JUDGE_SYSTEM using three of your labelled notes as examples. Remove those three from the set.
  3. Run the judge on the other 37. Compute agreement and kappa against your labels.
  4. Build the judge's 2×2 confusion matrix. Does it pass notes you failed, or fail notes you passed? Read every disagreement.
  5. Revise the rubric once and measure again. Did kappa rise?
  6. Bias test. Take five passing notes and pad each with two extra, accurate sentences, so they now break the one-sentence rule. How many does the judge still pass?
  7. If a second person can grade ten of the notes, compute kappa between the two of you. Compare it with your kappa against the judge.
