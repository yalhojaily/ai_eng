Monitoring quality drift

A system can get worse without anyone touching it. The model behind an API changes, users start asking different things, the data ages. No single trace shows it. Only numbers watched over time do, and choosing those numbers is the craft of this lesson.

Answer to last lesson's question. Both are true when the change is in the proportions. Suppose one answer in twenty used to be poor and now it is one in eight. Any trace you open is still most likely a good one, in either month. A decline like that is invisible run by run and obvious in a rate plotted over time. You would have noticed it if you had been computing that rate every day.

1. Four ways to get worse while standing still

What changedExample
The modelA provider updates the model behind a name, or retires the version you tuned for. Your prompts meet a different reader.
The inputsUsers arrive with a new kind of question, a new language, longer documents. The system was never evaluated on these.
The dataThe corpus is extended or re-indexed; documents go out of date; a tool's upstream source changes its format.
The worldNew words and topics appear that neither model nor corpus has seen.

Your eval set from Phase 3 guards against changes you make. It says nothing about changes that happen to you, and it is itself frozen at the moment you built it. Monitoring is evaluation that keeps running, on real traffic.

One defence belongs in configuration: request a specific, dated model version wherever the provider offers one, never a floating name that can be repointed. Then a model change becomes something you do deliberately, with the harness, instead of something you discover.

2. Language itself does not hold still

Linguists distinguish two ways of studying a language. A synchronic description captures it at one moment. A diachronic study follows it through time. Every corpus, every eval set and every trained model is synchronic: a snapshot. The language keeps moving after the shutter closes.

  • New words arrive. The Brown corpus you have been using was compiled from texts printed in 1961. It contains no email, no internet, no podcast.
  • Old words shift. Tablet, stream, cloud, viral and tweet have all gained meanings that a 1961 reader would not recognise. This is called semantic change.
  • Usage mixes. Communities develop new habits of spelling, borrowing and switching between languages, faster in informal writing than anywhere else.

For your agent this is concrete. Asked today about stream, it will report, correctly for its corpus, a word about water. A user will find that odd. The system did not break. The distance between its snapshot and the present grew. So among the things worth monitoring is a linguistic one: how much of what users ask about is missing from, or different in, your data.

3. What to watch

Everything here can be computed from the traces you began recording in Lesson 25.

KindSignalsTells you
Operationalrequests, error rate, latency, tokens and cost per requestwhether the service is up, fast and affordable
Behaviouralsteps per run, tool error rate, loop warnings, compactions, runs ended by a limitwhether the agent is working harder for the same result
Quality proxiesverifier failure rate, retries, abstention rate, "not found" rate, user ratings, how often users rephrase and ask againquality, indirectly, on every request, for free
Judged qualitya validated judge (Lesson 11) scoring a random sample of real traffic each day or weekquality, more directly, on a sample, at a cost
Inputslanguage mix, question length, share of words absent from the corpuswhether users have moved away from what you tested

The proxies are the workhorses. None of them is quality, and each can be gamed or can move for innocent reasons. But they are cheap, they cover every request, and a jump in one is a reason to read traces. And keep a human in the measurement: hand-check a small sample of the judge's verdicts regularly, because the judge is a model too, and its standards can drift along with everything else.

4. Averages lie about latency

Most requests are quick and a few are very slow, a shape statisticians call a long tail. In such a distribution the mean describes nobody's experience. So operations people report percentiles: the p50 (median) is the time half of requests beat; the p95 is the time 95% of requests beat, and one request in twenty is slower than it. Agents make the tail worse than usual, since one run takes four steps and another forty.

Try it · 1

Grow a tail

1,000 simulated requests. Most take about two seconds. Some fraction get stuck.

Experiments. Set stuck requests to 4%: the median and the p95 barely move while the mean climbs. Now 6%: the p95 jumps. Why does it react so sharply around 5%? And which number would a user who hit a slow request recognise?

5. Noticing a shift in a noisy number

A daily rate bounces around. The task is to tell a real change from an ordinary bounce, quickly, without crying wolf. The standard approach: establish what normal looks like over a baseline period, smooth the daily values with a rolling average over several days, and alert when the smoothed value crosses a threshold set some distance above normal.

Two settings, pulling against each other, in a trade you have met twice before as precision against recall:

  • A longer window and a higher threshold give fewer false alarms and slower detection.
  • A shorter window and a lower threshold give faster detection and more false alarms.
Try it · 2

Tune a drift alert

Sixty days of a quality proxy, the share of reports failing verification. Normal is about 4%. On day 30 something changes upstream.

Experiments. Set the window to 1 day and the threshold to 5%: how many false alarms before day 30? Now find settings that catch a 3-point shift within a week with none. Then set the shift to 1 point: can any setting catch it reliably? Small drifts need more data, which means more days, to detect at all. Press the noise button a few times before trusting a setting.

6. Alerts people act on

  • Few. An alert that fires weekly and is usually nothing teaches everyone to ignore alerts. Page a person only for what needs a person now; put the rest on a dashboard reviewed on a schedule.
  • Specific. "Verifier failure rate 9% over 7 days, normal 4%" with a link to failing traces, not "quality degraded".
  • With a next step. A short written procedure: check whether the model version changed, check the language mix, read ten failing traces, run the harness.
  • Closing the loop. Every investigated alert ends with new cases in the eval set (Lesson 12), so the same decline is caught before release next time.

Checkpoint

Lab: a dashboard from your traces

Time: 2 hours. Everything is computed from the span file written in Lesson 25.

import json, statistics
from collections import defaultdict
from datetime import datetime

def load_requests(path="traces/spans.jsonl"):
    spans = [json.loads(l) for l in open(path, encoding="utf-8")]
    by_trace = defaultdict(list)
    for s in spans:
        by_trace[s["trace"]].append(s)
    rows = []
    for trace_id, ss in by_trace.items():
        root = next(s for s in ss if s["parent"] is None)
        rows.append({
            "trace": trace_id,
            "day": datetime.fromtimestamp(root["start"]).date().isoformat(),
            "seconds": root["end"] - root["start"],
            "tokens": sum(s["attrs"].get("input_tokens", 0) + s["attrs"].get("output_tokens", 0) for s in ss),
            "steps": sum(s["kind"] == "model" for s in ss),
            "tool_errors": sum(s["kind"] == "tool" and "error" in s for s in ss),
            "verified": str(root["attrs"].get("verified")) == "True",
            "not_found": "No occurrences" in json.dumps(ss),    # the note your tools return (Lesson 20)
        })
    return rows

def percentile(values, p):
    values = sorted(values)
    return values[min(len(values) - 1, int(p / 100 * len(values)))]

def daily(rows):
    days = defaultdict(list)
    for r in rows:
        days[r["day"]].append(r)
    for day in sorted(days):
        rs = days[day]
        print(day, f"n={len(rs):3}",
              f"p50={percentile([r['seconds'] for r in rs], 50):5.1f}s",
              f"p95={percentile([r['seconds'] for r in rs], 95):5.1f}s",
              f"tokens/req={statistics.mean(r['tokens'] for r in rs):7.0f}",
              f"verify_fail={1 - statistics.mean(r['verified'] for r in rs):.2f}",
              f"not_found={statistics.mean(r['not_found'] for r in rs):.2f}")

def alert(series, window=7, threshold=0.055):
    """series: list of daily rates. Returns the indexes of days on which the alert fires."""
    return [i for i in range(window - 1, len(series))
            if statistics.mean(series[i - window + 1:i + 1]) > threshold]
  1. Make sure the root span records verified, the model ID and the prompt version. Run forty reports on ordinary words to establish a baseline. Print the daily table.
  2. Simulate input drift. Run twenty reports on words the 1961 corpus lacks or uses differently: email, internet, online, stream, tablet, viral, cloud. Which columns move? Which stay flat although quality has plainly fallen?
  3. Add an input signal: the share of requested words with zero or very low corpus frequency. Does it catch the drift sooner than the output signals?
  4. Simulate a model change. Switch MODEL to a weaker model for twenty runs without telling your dashboard. Which signals show it?
  5. Write an alert rule for one signal with a window and a threshold, and test it on your combined series. How many days of the bad period passed before it would have fired?
  6. Sample ten reports from each period, shuffle them, and grade them blind against Lesson 24's rubric. Does your own judgement agree with what the proxies said?
