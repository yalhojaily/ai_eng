Evaluating agents

An agent that worked when you tried it has been observed to work once. Agents take different paths on different runs, fail in ways a final answer hides, and cost amounts that vary by a factor of ten. Measuring them takes everything from Phase 3 and three new ideas.

Answer to last lesson's question. Almost nothing. You know that one path, on one word, on one occasion, produced a report that convinced you. You do not know whether it would do so again, whether it works for other words, whether the report was right or merely fluent, or what it cost. Each of those gaps is a section of this lesson.

1. What makes agents harder to evaluate

  • They vary. The same input can lead to different sequences of steps and different answers. One run is one sample.
  • There are many right paths. You cannot compare the steps against a single reference sequence.
  • The outcome hides the process. A correct answer reached by a lucky guess, or by twenty wasted calls, looks the same as a sound one.
  • Cost is part of the result. Two agents of equal accuracy can differ tenfold in tokens and time.

So an agent is measured on three things together: the outcome (was the result right?), the trajectory (was the path sound and economical?) and the cost.

2. Ground truth from code

Your agent works over a corpus you hold, so a whole class of questions has answers a script can compute exactly. That gives you an outcome eval with no human labelling and no judge:

Task for the agentGround truth from code
In which genre is issue most frequent per million words?recount and normalise
Does serendipity occur in the fiction section?search
What word most often follows run in news?count the next word
Is light more often preceded by the or by in in learned prose?count the previous word

These are narrower than "describe how the word is used", and that is their value. An agent that cannot answer them reliably cannot be trusted with the open task, and when it fails, you know exactly which fact it got wrong. Include tasks whose true answer is "no" or "it does not occur": they test whether the agent reports absence correctly instead of inventing a finding.

For the open task, the report, combine three measures you already have: the verifier's pass rate (Lesson 23), a rubric scored by a validated judge (Lesson 11), and a sample you read yourself.

3. Reliability: run it more than once

Suppose an agent succeeds on a task 80% of the time. Try it once and you will most likely see it work, and conclude it works. A user who relies on it every day will see it fail one day in five. Averages over tasks hide this: "80% accuracy" could mean 80 tasks always solved and 20 never, or every task solved four times in five. These are very different products.

So run every task several times, and report two numbers: the average success rate, and the share of tasks solved on every one of k runs. The second is the measure of dependability, and it falls quickly as k rises.

Once is not evidence

Experiments. At 80%, how likely is a single trial to succeed and mislead you? How many runs before "succeeds every time" drops below one in three? What per-run rate do you need for ten consecutive successes to be more likely than not?

4. Scoring the trajectory

You saved every trace in Lesson 22. From a trace, code can compute:

  • Efficiency: steps, tool calls, tokens, seconds.
  • Waste: repeated calls, calls whose results were never used, loop warnings triggered.
  • Soundness: did it call frequency before making a claim about frequency? Did it examine every genre it made claims about? Were all cited IDs returned by some tool call in this run?
  • Health: tool errors, gate rejections, retries, compactions, whether a limit was hit.

Soundness checks are the important ones. They test the method, which is how you catch the right answer reached the wrong way, such as a correct frequency ranking stated from the model's memory with no tool call behind it.

5. Three layers of testing

  
As with any software, test the parts as well as the whole:

  
    
    
  • Tools: ordinary unit tests. frequency("run") returns the right numbers; an unknown genre returns the helpful error. No model involved, runs in milliseconds, and catches the bugs that would otherwise look like agent failures.
    • 
    
  • Single steps: give the model a fixed context and check its next action. Given the question and a frequency result, does it ask for a concordance next? Useful for testing prompt changes cheaply.
    • 
    
  • Whole runs: the outcome, trajectory and cost measures above. Slow and costly, so keep the task set small and well chosen.
    • 
  


  
6. In practice

  
    
    
  • Twenty good tasks beat two hundred careless ones. Each whole-run task is expensive. Choose tasks that cover the tools, the genres, absent words, ambiguous words and at least one planted injection.
    • 
    
  • Always report cost with accuracy. "71% at 9,000 tokens per task" and "74% at 80,000" are both honest descriptions of real trade-offs. An accuracy figure alone invites the second without anyone having chosen it.
    • 
    
  • Compare versions with Lesson 12's tools. Per-task diffs, fixed and broken lists, a sign test. With repeated runs, count a task as fixed only if it moved from mostly failing to mostly passing.
    • 
    
  • Keep reading traces. Metrics tell you that step counts rose. Only reading shows you that the agent now checks every genre twice because of a sentence you added to the prompt.
    • 
    
  • Turn failures into tasks. Every surprising trace from real use becomes a new item in the set (Lesson 12).

def truth_top_genre(word):
    f = frequency(word)                      # your tool, called directly as a function
    return max(GENRES, key=lambda g: f[g]["per_million"])

def truth_occurs(word, genre):
    return concordance(word, genre)["total"] > 0

TASKS = [
    {"id": "top-issue", "question": "In which genre is 'issue' most frequent per million words? "
                                    "Answer with the genre name only.",
     "check": lambda answer: truth_top_genre("issue") in answer.lower()},
    {"id": "absent-1",  "question": "Does the word 'serendipity' occur in the fiction genre? "
                                    "Answer yes or no, then one sentence.",
     "check": lambda answer: answer.lower().startswith("yes" if truth_occurs("serendipity", "fiction") else "no")},
    # ... 18 more: next-word and previous-word counts, comparisons, absent words, one injection ...
]

def trajectory_metrics(trace):
    """trace: list of {"name": ..., "args": ..., "result": ...} for one run"""
    calls = [(c["name"], json.dumps(c["args"], sort_keys=True)) for c in trace]
    return {
        "tool_calls": len(calls),
        "repeated": len(calls) - len(set(calls)),
        "errors": sum("error" in str(c["result"])[:40] for c in trace),
        "used_frequency": any(n == "frequency" for n, _ in calls),
    }

def evaluate(tasks, runs=3):
    rows = []
    for task in tasks:
        passes, tokens, steps = 0, 0, 0
        for _ in range(runs):
            answer, trace, usage = run_agent_traced(task["question"])   # returns all three
            passes += bool(task["check"](answer))
            tokens += usage; steps += len(trace)
        rows.append({"id": task["id"], "pass_rate": passes / runs, "all_pass": passes == runs,
                     "avg_tokens": tokens // runs, "avg_calls": steps / runs})
    n = len(rows)
    print(f"mean success {sum(r['pass_rate'] for r in rows) / n:.2f}   "
          f"solved every time {sum(r['all_pass'] for r in rows) / n:.2f}   "
          f"avg tokens {sum(r['avg_tokens'] for r in rows) // n}")
    return rows
